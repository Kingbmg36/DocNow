# Deploying DocNow.NG to Render

Switched from Railway to Render after hitting both platform-side build flakiness and
dashboard settings (Root Directory, Builder) that reset when a service got
recreated. Render's Blueprint (`render.yaml`, committed to this repo) avoids the
second problem entirely — the Docker build scope for each service is explicit in
version-controlled YAML, not a clickable dashboard field that can drift.

```
┌─ Render Blueprint (render.yaml) ─────────────────────┐
│  docnow-backend  (Docker, backend/) ── MONGO_URL ─────┼──▶ MongoDB Atlas (M0 free)
│  docnow-frontend (static site, frontend/) ── REACT_APP_BACKEND_URL ─▶ backend
└────────────────────────────────────────────────────────┘
```

## 0. What you'll need

Same as the Railway runbook (`DEPLOY.md`) — already in hand from that attempt:
- GitHub repo (already pushed: `Kingbmg36/DocNow`)
- MongoDB Atlas connection string
- Anthropic API key
- *(optional)* Paystack / Resend / Termii / Meta WhatsApp keys — everything defaults
  to safe stub mode without them

Plus a free **Render** account (render.com).

---

## 1. Deploy the Blueprint

1. Render dashboard → **New → Blueprint**.
2. Connect the `Kingbmg36/DocNow` GitHub repo (Render's GitHub App needs access —
   authorize it if this is the first time).
3. Render detects `render.yaml` at the repo root automatically and shows both
   services (`docnow-backend`, `docnow-frontend`) it's about to create.
4. Click **Apply** — it creates both services and does an initial deploy, but the
   backend will fail to boot until step 2 below fills in the required secrets
   (marked `sync: false` in `render.yaml` — Render prompts for these during the
   blueprint wizard, or you fill them in afterward under each service's
   **Environment** tab).

---

## 2. Fill in backend secrets

`docnow-backend` → **Environment** tab. Required (the blueprint declares the rest with
safe defaults):

| Variable | Value |
|---|---|
| `MONGO_URL` | Atlas connection string (`mongodb+srv://user:pass@cluster0.xxxx.mongodb.net/...`) |
| `ADMIN_EMAIL` / `ADMIN_PASSWORD` | your admin login |
| `ANTHROPIC_API_KEY` | `sk-ant-…` |
| `FRONTEND_URL` | fill in **after** step 3, once the frontend URL exists |

`JWT_SECRET` is auto-generated by Render (`generateValue: true` in the blueprint) —
nothing to do there. `DB_NAME`, `SEED_WIPE`, `DEV_OTP_REVEAL`, `ANTHROPIC_MODEL`, and
every integration's `_ENABLED` flag already have safe values baked into `render.yaml`.

Save → this redeploys the backend automatically.

---

## 3. Frontend URL wiring

1. Once `docnow-frontend` has deployed, copy its URL (Render assigns something like
   `https://docnow-frontend.onrender.com`, or set a custom domain under
   **Settings → Custom Domains**).
2. `docnow-frontend` → **Environment** → set `REACT_APP_BACKEND_URL` to the
   **backend's** URL (`https://docnow-backend.onrender.com`, no trailing slash).
   This is baked in at **build time** (CRA), so setting it triggers a rebuild.
3. Go back to `docnow-backend` → **Environment** → set `FRONTEND_URL` to the
   frontend's URL from step 1. Save (redeploys the backend — quick, since the image
   layers are cached).

---

## 4. Paystack webhook (if `PAYSTACK_ENABLED=true`)

Paystack dashboard → **Settings → API Keys & Webhooks** → webhook URL:

```
https://<docnow-backend-url>/api/payments/webhook
```

HMAC-SHA512 verified server-side — this is the authoritative payment-fulfilment path.

---

## 5. First boot & smoke test

`seed_admin_and_demo()` runs on backend startup and creates the admin/demo
doctor/patient — it does **not** wipe existing data (`SEED_WIPE=false`).

1. `GET https://<docnow-backend-url>/api/health` → `{"status":"healthy"}`
2. Open the frontend URL → log in as admin.
3. Register a doctor, upload a license, approve it as admin.
4. As a patient: symptom checker (exercises Claude), book → pay (stub or Paystack
   test card, depending on `PAYSTACK_ENABLED`).

---

## Why not Railway (context for later)

Not a knock on Railway generally — this specific session hit:
- Deploys stuck in `QUEUED` for 15+ min with zero build log output (Railway's own
  "upstream GitHub issues" message), even after they said it was resolved.
- Direct CLI (`railway up`, bypassing GitHub) deploys failing at
  `scheduling build on Metal builder "..."` with zero output — a builder-side issue,
  reproduced 3x across different deployments.
- Mid-session, the service was silently renamed and re-ID'd (`DocNow` →
  `natural-nurturing`), which reset its Root Directory / Builder settings — a real,
  reproducible instance of exactly the dashboard-drift problem `render.yaml`
  avoids by keeping build scope in git instead.

If you want to revisit Railway later, `backend/railway.json` / `frontend/railway.json`
and `DEPLOY.md` are still in the repo, untouched.
